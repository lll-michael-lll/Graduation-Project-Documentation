\section{Detailed Architecture}

The zGate platform is architected as a distributed system comprising three primary components: the Gateway Server, Web UI, and CLI. Each component is designed with specific responsibilities that collectively implement Zero Trust database access.

% ============================================================
\subsection{System Components Overview}

The zGate architecture can be conceptualized as a multi-layered security gateway that intercepts, validates, and controls all database access. Figure~\ref{fig:complete-system-flow} illustrates the complete data flow across all system components.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{images/images for doc/Complete system data flow.png}
    \caption{Complete System Data Flow Architecture}
    \label{fig:complete-system-flow}
\end{figure}

The system architecture follows a clear separation of concerns:

\begin{itemize}[leftmargin=*]
    \item \textbf{Client Layer:} WebUI and CLI provide user interfaces for authentication and database connection management
    \item \textbf{API Layer:} RESTful API server handles authentication, authorization, and session management
    \item \textbf{Gateway Layer:} Protocol-aware proxy intercepts and controls database traffic
    \item \textbf{Data Layer:} Target databases are accessed through the gateway with enforced security policies
    \item \textbf{Storage Layer:} MySQL database stores users, roles, permissions, and audit logs
    \item \textbf{Policy Engine:} Safety templates, masking policies, and rate limits are evaluated per query
    \item \textbf{Compliance Layer:} Built-in regulatory frameworks automate policy configuration
    \item \textbf{AI Service Layer:} LLM integration powers column classification, anomaly detection, and the admin chat assistant
    \item \textbf{PKI Layer:} Internal certificate authority issues and revokes mTLS client certificates
\end{itemize}

\begin{enumerate}[leftmargin=*]
    \item \textbf{Server:} Orchestrates the lifecycle of database handlers and manages protocol-specific processing
    \item \textbf{Listener:} Manages TCP listener lifecycle for dynamic port allocation per user session
    \item \textbf{Acceptor:} Handles incoming client connections and establishes connection metadata
    \item \textbf{Dispatcher:} Establishes backend database connections and manages bidirectional traffic forwarding
    \item \textbf{Manager:} Coordinates session lifecycle, credential provisioning, and resource cleanup
    \item \textbf{Interceptor Chain:} Provides composable query processing pipeline for security enforcement
\end{enumerate}

\paragraph{Server Component}

The Server component (\texttt{internal/gateway/server.go}) serves as the orchestration layer for the gateway. Its primary responsibilities include:

\begin{itemize}[leftmargin=*]
    \item \textbf{Handler Initialization:} Pre-initializes protocol handlers for all registered database types (MySQL, PostgreSQL, MSSQL, MariaDB)
    \item \textbf{TLS Configuration:} Manages end-to-end TLS encryption for proxy-to-database connections with support for certificate pinning
    \item \textbf{Handler Registry:} Maintains a type-to-handler mapping that enables protocol-specific processing
    \item \textbf{Resource Sharing:} Provides thread-safe access to shared handlers across multiple sessions
\end{itemize}

\textbf{Input:} Database configurations from MySQL store, TLS certificate paths\\
\textbf{Output:} Initialized handlers for each database type\\
\textbf{Communication:} Provides handlers to Manager component via GetHandler() method

\paragraph{Manager Component}

The Manager component (\texttt{internal/proxy/manager.go}) implements the session lifecycle management with sophisticated credential provisioning logic. It follows a three-tier account priority system:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Personal Accounts:} Dedicated database accounts assigned to specific users
    \item \textbf{Shared Accounts:} Pool of pre-created accounts shared across users with concurrent usage limits
    \item \textbf{Ephemeral Accounts:} Temporary accounts created on-demand and destroyed on disconnect
\end{enumerate}

\textbf{Session Creation Workflow:}
\begin{enumerate}[leftmargin=*]
    \item Validates user permissions for requested database using real-time policy evaluation
    \item Attempts to retrieve personal database account from store
    \item If unavailable, checks shared account pool for available credentials
    \item If pool exhausted, creates ephemeral temporary database user with scoped permissions
    \item Allocates dynamic port from operating system
    \item Initializes session context and starts listener
    \item Returns connection details to API layer
\end{enumerate}

The Manager also listens for role-change notifications from the service layer. When an administrator updates a user's roles or deletes a user, the Manager immediately terminates all active sessions belonging to that user — ensuring access revocation takes effect without waiting for JWT expiry.

    \centering
    \includegraphics[width=0.65\textwidth]{images/acc_types.jpg}
    \caption{Account Types}
    \label{fig:acc-types}
\end{figure}
\textbf{Input:} JWT claims, database name, user permissions\\
\textbf{Output:} Session object with port, credentials, account type\\
\textbf{Communication:} Interacts with Store for credentials, Gateway Server for handlers, Database for ephemeral user creation

\paragraph{Listener Component}

The Listener component (\texttt{internal/gateway/listener.go}) manages the TCP listener lifecycle for each user session. Each session receives a dedicated listener on a dynamically allocated port.

\textbf{Key Responsibilities:}
\begin{itemize}[leftmargin=*]
    \item Creates TCP listener on specified port (0.0.0.0:port for remote mode, configurable for security)
    \item Accepts incoming client connections in a loop
    \item Delegates each connection to Acceptor for processing
    \item Implements graceful shutdown via context cancellation
    \item Tracks active connections using WaitGroup for clean termination
\end{itemize}

\textbf{Input:} Listen address, database configuration, session metadata\\
\textbf{Output:} Accepted client connections\\
\textbf{Communication:} Spawns Acceptor for each connection

\paragraph{Acceptor Component}

The Acceptor component (\texttt{internal/gateway/acceptor.go}) processes each incoming client connection from acceptance to completion.

\textbf{Responsibilities:}
\begin{itemize}[leftmargin=*]
    \item Captures client connection metadata (IP address, timestamp)
    \item Associates connection with session ID for audit correlation
    \item Creates ConnectionMetadata structure with user context
    \item Delegates to Dispatcher for protocol handshake and traffic forwarding
    \item Ensures proper connection cleanup on termination
\end{itemize}

\textbf{Input:} Client TCP connection, database credentials, session metadata\\
\textbf{Output:} ConnectionMetadata structure\\
\textbf{Communication:} Instantiates Dispatcher for bidirectional proxying

\paragraph{Dispatcher Component}

The Dispatcher component (\texttt{internal/gateway/dispatcher.go}) is responsible for establishing backend connections and managing the entire query lifecycle.

\textbf{Connection Establishment:}
\begin{enumerate}[leftmargin=*]
    \item Establishes TCP connection to backend database server
    \item Configures protocol handler with target database and proxy credentials
    \item Performs authentication handshake using real database credentials
    \item Handles TLS upgrade for both client-proxy and proxy-backend connections
    \item Extracts upgraded connections from handshake result
\end{enumerate}

\textbf{Query Processing Loop:}
\begin{enumerate}[leftmargin=*]
    \item Reads command from client connection using protocol handler
    \item Creates QueryContext with session metadata
    \item Invokes BeforeQuery interceptor chain (safety checks, rate limiting, logging)
    \item Forwards allowed queries to backend database
    \item Receives query results from database, row by row
    \item Invokes OnRow interceptor for each result row (masking, AI classification)
    \item Invokes AfterQuery interceptor chain (anomaly detection, audit logging)
    \item Forwards processed results back to client
\end{enumerate}

\textbf{Input:} Client and backend connections, database credentials, interceptor configuration\\
\textbf{Output:} Processed query results with security enforcement applied\\
\textbf{Communication:} Coordinates between Protocol Handler, Interceptor Chain, and both client and database

\paragraph{Interceptor Chain}

The Interceptor Chain (\texttt{internal/proxy/interceptor/}) implements a composable pipeline for query processing. The CompositeInterceptor orchestrates all configured interceptors in the following fixed order:

\begin{enumerate}[leftmargin=*]
    \item \textbf{Logging Interceptor} — Structured audit log entry before and after execution
    \item \textbf{Routing Boundary Check} — Validates the query targets the permitted database scope
    \item \textbf{Rate Limiting Interceptor} — Enforces per-role queries-per-second limits
    \item \textbf{Safety Interceptor} — Evaluates query against configurable safety template rules
    \item \textbf{Policy Masking Interceptor} — Applies column-level masking according to masking policies
    \item \textbf{Row Masking Interceptor} — Filters out rows matching row-level masking conditions
    \item \textbf{AI Masking Interceptor} — Applies semantic masking to AI-classified sensitive columns
    \item \textbf{Anomaly Detection Interceptor} — Scores behaviour against baseline, raises alerts
\end{enumerate}

The chain fires three hook points: \textbf{BeforeQuery} (steps 1–4), \textbf{OnRow} per result row (steps 5–7), and \textbf{AfterQuery} (step 8). An \textbf{OnError} callback is always invoked when any hook returns an error, allowing the logging interceptor to record failures.

\vspace{0.3cm}

\textbf{Logging Interceptor}

\textit{Purpose:} Provides comprehensive audit trail for all database operations.

\textbf{Functionality:}
\begin{itemize}[leftmargin=*]
    \item Captures query text, timestamp, user identity, target database
    \item Records query execution duration and rows affected
    \item Filters internal/system queries (SET, SHOW, SELECT @@)
    \item Writes structured logs to file for compliance and forensics
\end{itemize}

\vspace{0.3cm}

\textbf{Safety Interceptor}

\textit{Purpose:} Evaluates queries against configurable safety template rules (see Section~\ref{subsec:query-policy-engine}).

\textbf{Rule Actions:}
\begin{itemize}[leftmargin=*]
    \item \textbf{block} — Query rejected immediately with an error returned to the client
    \item \textbf{warn} — Query stored in the warned\_queries table for admin review; execution paused
    \item \textbf{require\_where} — Query blocked if it lacks a WHERE clause
    \item \textbf{allow} — Explicit allowance (useful to override template defaults)
\end{itemize}

\vspace{0.3cm}

\textbf{Masking Interceptors}

Three complementary masking interceptors operate on result rows, each covering a different classification approach. Full details are provided in Section~\ref{subsec:masking-architecture}.

\vspace{0.3cm}

\textbf{Anomaly Detection Interceptor}

\textit{Purpose:} Detects behavioural anomalies and raises alerts for administrator review.

\textbf{Signals monitored:}
\begin{itemize}[leftmargin=*]
    \item Unusually high query volume (rate spikes)
    \item Access to tables outside a user's normal scope
    \item Large result sets exceeding historical averages
    \item Queries executed at unusual hours
    \item Sequential scan patterns indicative of data exfiltration
\end{itemize}

Each anomaly is scored, tagged with a reason array and a correlation ID that groups related alerts, and written to the \texttt{anomaly\_notifications} table for admin consumption (see Section~\ref{subsec:anomaly-detection}).

\subsection{Authentication System}
\label{subsec:authentication}

The authentication system implements JWT-based token authentication with automatic token rotation for enhanced security. The system supports multiple authentication schemes to suit different deployment and operational needs.

\subsubsection{Authentication Schemes}

\begin{itemize}[leftmargin=*]
    \item \textbf{Username / Password (Local):} Traditional credential-based login where passwords are verified (bcrypt) and a JWT pair (access + refresh) is issued. Login requests must additionally satisfy an anti-bot challenge (ALTCHA proof-of-work or an arithmetic puzzle) to prevent automated credential-stuffing attacks.
    \item \textbf{TOTP / Multi-Factor Authentication:} Users may enrol a time-based one-time password authenticator (TOTP). Once activated, the login flow validates the TOTP code in addition to the password.
    \item \textbf{OIDC / Keycloak Device Flow:} The CLI uses an OIDC device-authorization grant against a Keycloak realm to obtain tokens without embedding a client secret. The backend exchanges the Keycloak identity token for a zGate JWT via \texttt{POST /api/auth/oidc/exchange}.
    \item \textbf{Service Account Tokens:} Automated processes authenticate using a client-ID/secret pair issued to a service account, bypassing human authentication flows.
    \item \textbf{Mutual TLS (mTLS) Client Certificates:} When \texttt{ENFORCE\_MTLS=true}, both human users and service accounts authenticate using X.509 certificates signed by the internal CA. The gateway validates the client certificate during the TLS handshake and maps it to a principal identity.
\end{itemize}

\subsubsection{Anti-Bot Challenges}

To prevent credential-stuffing and bot-driven brute-force attacks, every login request must first solve one of two challenge mechanisms:

\textbf{1. ALTCHA Proof-of-Work}

ALTCHA is a client-side proof-of-work challenge (\texttt{GET /api/altcha/challenge}). The client performs a computationally expensive hashing task before submission. The server verifies the solution is valid, was issued recently, and has not been replayed (replay-attack detection via HMAC).

\textbf{2. Arithmetic Puzzle}

An alternative lightweight challenge (\texttt{GET /api/puzzle/challenge}) issues a simple arithmetic problem whose answer must accompany the login request. Both challenge types are rate-limited independently to throttle challenge generation.

\subsubsection{TOTP Enrolment and Verification}

\subsubsection{OIDC / Keycloak Device Flow}

The CLI supports passwordless login via the OIDC device-authorization flow:

\begin{enumerate}[leftmargin=*]
    \item CLI initiates device-flow authorization against the Keycloak realm
    \item User authenticates in a browser (including Keycloak OTP if configured in the realm)
    \item Keycloak issues an identity token to the CLI
    \item CLI presents the Keycloak identity token to \texttt{POST /api/auth/oidc/exchange}
    \item zGate backend validates the token against the JWKS URL, creates or syncs the local user record, and issues a zGate JWT pair
    \item A background sync routine keeps zGate users in sync with the Keycloak realm (creating and removing accounts as the realm changes)
\end{enumerate}

\textbf{Authentication Process:}
\begin{enumerate}[leftmargin=*]
    \item Client solves anti-bot challenge (ALTCHA PoW or arithmetic puzzle)
    \item Client submits credentials and challenge solution to \texttt{POST /api/login}
    \item API verifies challenge solution (HMAC/replay check)
    \item API invokes Authenticator component to verify password using bcrypt
    \item If TOTP is enrolled, TOTP code is validated

    \item Store creates refresh token (7-day expiration) linked to user session
    \item Response includes both tokens, token type, expiration, and username
    \item Client stores tokens securely (OS keyring for CLI, memory for WebUI)
\end{enumerate}

\subsubsection{Token Refresh Flow}

Figure~\ref{fig:token-refresh} shows the token refresh mechanism that implements automatic token rotation for security.

\begin{figure}[H]

\textbf{Token Rotation Security:}
\begin{itemize}[leftmargin=*]
    \item Client submits current refresh token to \texttt{POST /api/refresh}
    \item Store validates refresh token and retrieves associated username
    \item New access token is generated with updated permissions
    \item New refresh token is created to replace the old one
    \item Old refresh token is immediately revoked in database
    \item Both new tokens are returned to client
    \item Prevents token reuse attacks and limits blast radius of token compromise
\end{itemize}

\subsection{Admin Access-Control Tiers}
\label{subsec:admin-tiers}

zGate implements a four-tier administrative access-control model to enforce least-privilege among administrators themselves. Each tier is stored in the \texttt{accounts.tier} column and enforced by a \texttt{tierMiddleware} in the API layer.

\begin{figure}[H]
    \centering
    % [PLACEHOLDER: Admin tier hierarchy diagram showing permission scopes]
    \fbox{\parbox{0.75\textwidth}{\centering\vspace{1.5cm}\textit{[PLACEHOLDER: Admin Access-Control Tier Diagram]}\vspace{1.5cm}}}
    \caption{Admin Access-Control Tier Hierarchy}
    \label{fig:admin-tiers}
\end{figure}

\begin{enumerate}[leftmargin=*]
    \item \textbf{Super Admin:} Full system access including admin account management, LLM configuration, and tier assignment. Can perform all operations. Only a super admin can promote another account to super.
    \item \textbf{DB Admin:} Manages users, databases, database accounts (personal, shared, ephemeral), service accounts, and roles. Cannot modify admin accounts or system-wide policies.
    \item \textbf{Policy Admin:} Manages rate limits, safety templates, masking policies, row masking, AI masking, anomaly alerts, and compliance framework assignments. Cannot modify users or database configurations.
    \item \textbf{Auditor:} Read-only access to all logs, session activity, query history, and configuration snapshots. Cannot modify any data.
\end{enumerate}

Super admins assign tiers via \texttt{PATCH /api/admin/admins/\{username\}/tier}. The tier system ensures that a compromised policy admin cannot exfiltrate credentials, and a compromised auditor cannot alter policies.

\subsection{Service Accounts and Programmatic Access}
\label{subsec:service-accounts}

Service accounts provide a first-class authentication primitive for automated processes, CI/CD pipelines, ETL jobs, and microservices that require database access without human interaction.

\subsubsection{Service Account Authentication Modes}

\begin{itemize}[leftmargin=*]
    \item \textbf{Token-Based:} Service account authenticates using a client-ID and secret (\texttt{POST /api/auth/service-account/token}). Tokens are short-lived and must be refreshed.
    \item \textbf{mTLS Certificate:} When mTLS enforcement is active, service accounts present a client certificate signed by the zGate internal CA. No secret is transmitted on the wire.
    \item \textbf{Direct Connect:} \texttt{POST /api/auth/service-account/connect} combines authentication and session creation in a single request for use by the headless tunnel command.
\end{itemize}

\subsubsection{Service Account Lifecycle}

\begin{figure}[H]
    \centering
    % [PLACEHOLDER: Service account lifecycle – create, issue cert, connect, rotate, suspend, revoke]
    \fbox{\parbox{0.75\textwidth}{\centering\vspace{1.5cm}\textit{[PLACEHOLDER: Service Account Lifecycle Flow]}\vspace{1.5cm}}}
    \caption{Service Account Lifecycle Management}
    \label{fig:service-account-lifecycle}
\end{figure}

\begin{enumerate}[leftmargin=*]
    \item \textbf{Create:} DB Admin creates a service account with a name, description, and optional IP allowlist
    \item \textbf{Issue Certificate:} Admin issues an mTLS certificate via \texttt{POST /api/admin/service-accounts/\{id\}/issue-certificate}; the signed certificate and private key are returned once and never stored by the server
    \item \textbf{Connect:} Service account presents certificate (or token) to authenticate and obtain a proxy session
    \item \textbf{Rotate Secret:} \texttt{POST /api/admin/service-accounts/\{id\}/rotate-secret} invalidates the old token and issues a new one
    \item \textbf{Rotate Certificate:} \texttt{POST /api/admin/service-accounts/\{id\}/rotate-certificate} revokes the existing cert and issues a replacement in one atomic operation
    \item \textbf{Suspend / Activate:} Temporarily disables access without deleting the account
    \item \textbf{Revoke:} Permanently invalidates all tokens and certificates; active sessions are terminated
\end{enumerate}

Service accounts follow the same three-tier account-type priority (personal → shared → ephemeral) as human users.

\subsection{PKI and Mutual TLS Client Certificates}
\label{subsec:pki-mtls}

zGate operates an internal Certificate Authority (CA) to issue and manage X.509 client certificates for both human users and service accounts. This eliminates reliance on external PKI infrastructure and enables fine-grained certificate lifecycle management.

\subsubsection{Internal CA}

The CA is initialised on first start and stored in the \texttt{pki\_ca} table (single row) with the certificate PEM in plaintext and the private key encrypted using AES-256-GCM. CA rotation is supported via admin operation without disrupting existing valid certificates.

\begin{itemize}[leftmargin=*]
    \item \textbf{Human Users (self-service):} \texttt{POST /api/auth/me/issue-certificate} — user requests their own certificate; signed certificate returned in response
    \item \textbf{Human Users (admin):} \texttt{POST /api/admin/accounts/\{id\}/issue-certificate} — admin issues cert for any user
    \item \textbf{Service Accounts:} \texttt{POST /api/admin/service-accounts/\{id\}/issue-certificate}

    \item \textbf{Rotation:} Atomic revoke-and-reissue in a single API call
\end{itemize}

\subsubsection{mTLS Enforcement Modes}

\begin{itemize}[leftmargin=*]
    \item \textbf{\texttt{ENFORCE\_MTLS=true}:} Strict mode. All clients must present a valid, unrevoked client certificate. Ticket-based legacy mode is disabled. No plaintext credential exchange occurs on the proxy port.
    \item \textbf{\texttt{ENFORCE\_MTLS=false}:} Permissive mode. mTLS is optional. Ticket-based credential injection remains available for JDBC clients that cannot present certificates (e.g., legacy tooling).
\end{itemize}

The server CA fingerprint and current mTLS mode are exposed via \texttt{GET /api/config} so that CLI tools can auto-configure trust anchors without manual certificate distribution.

\subsection{Database Connection Lifecycle}

The database connection lifecycle implements the core Zero Trust principle: users never handle production credentials. The system manages three types of database accounts with different lifecycle characteristics.

\subsubsection{Database Account Types}

The zGate platform implements a sophisticated three-tier account management system that eliminates credential exposure while optimizing resource utilization and security. Each account type serves a distinct purpose in the Zero Trust architecture:

\paragraph{Personal Database Accounts}

Personal accounts represent the highest privilege tier, providing dedicated database credentials assigned exclusively to individual users.

\textbf{Creation and Provisioning:}
\begin{itemize}[leftmargin=*]
    \item Administrators pre-create accounts through the WebUI administrative interface
    \item Each account is permanently associated with a specific user via user\_id mapping
    \item Credentials are stored encrypted in the zGate database
    \item Account permissions are configured at the database level by DBAs
\end{itemize}

\textbf{Usage Scenario:}
\begin{itemize}[leftmargin=*]
    \item When a user with a personal account requests database access, zGate immediately retrieves their dedicated credentials
    \item No account creation overhead or waiting time
    \item User maintains consistent database identity across sessions
    \item Ideal for privileged users, developers, or users requiring specific database roles
\end{itemize}

\textbf{Lifecycle and Advantages:}
\begin{itemize}[leftmargin=*]
    \item Accounts persist indefinitely across sessions and disconnections
    \item Provides accountability through consistent database audit trails
    \item Enables fine-grained permission management at the user level
    \item Eliminates runtime account provisioning latency
\end{itemize}

\paragraph{Shared Account Pool}

Shared accounts implement a connection pool pattern, enabling multiple users to share a limited set of pre-provisioned database accounts.

\textbf{Creation and Pool Management:}
\begin{itemize}[leftmargin=*]
    \item Administrators create a pool of generic database accounts via WebUI
    \item Each account has configurable concurrent usage limits (\texttt{max\_concurrent\_users})
    \item Pool size is determined by anticipated concurrent load
    \item Accounts are tagged as \texttt{shared} in the account type field
\end{itemize}

\textbf{Usage Scenario:}
\begin{itemize}[leftmargin=*]
    \item When a user without a personal account connects, zGate queries the pool for available accounts
    \item An account is considered available if \texttt{currently\_in\_use < max\_concurrent\_users}
    \item Upon assignment, the \texttt{currently\_in\_use} counter is atomically incremented
    \item Multiple users can share the same database account simultaneously within the limit
    \item Ideal for read-only users, analysts, or scenarios with many concurrent users
\end{itemize}

\textbf{Lifecycle and Advantages:}
\begin{itemize}[leftmargin=*]
    \item Accounts remain persistent but are released back to the pool on disconnect
    \item The \texttt{currently\_in\_use} counter is decremented when the session ends
    \item Significantly reduces database account sprawl compared to per-user accounts
    \item Optimizes resource utilization in environments with high user counts
    \item Provides a balance between security and operational overhead
\end{itemize}
\begin{figure}[H]
    \centering
    \includegraphics[width=0.65\textwidth]{images/shared_acc.jpg}
    \caption{Shared Account Pool Management}
    \label{fig:shared-acc}
\end{figure}

\paragraph{Ephemeral Temporary Accounts}

Ephemeral accounts represent the ultimate Zero Trust approach: credentials that exist only for the duration of a single database session.

\textbf{Creation and Provisioning:}
\begin{itemize}[leftmargin=*]
    \item Created on-demand by the Gateway Manager component when no personal or shared accounts are available
    \item zGate connects to the database using a privileged provisioning account
    \item Executes \texttt{CREATE USER} with a cryptographically random username and password
    \item Grants appropriate permissions based on the user's role permissions from zGate
    \item Account details are stored only in memory within the active session context
\end{itemize}
\begin{figure}[H]
    \centering
    \includegraphics[width=0.65\textwidth]{images/ephemeral.png}
    \caption{Ephemeral Account Creation}
    \label{fig:ephemeral}
\end{figure}
\textbf{Usage Scenario:}
\begin{itemize}[leftmargin=*]
    \item Triggered when personal account doesn't exist and shared pool is exhausted
    \item Entire account lifecycle contained within a single zGate session
    \item User never sees or handles the actual database credentials
    \item Ideal for untrusted environments or maximum security requirements
\end{itemize}

\textbf{Lifecycle and Advantages:}
\begin{itemize}[leftmargin=*]
    \item Account is deleted immediately upon session disconnect via \texttt{DROP USER}
    \item Credentials become invalid within seconds of session termination
    \item Zero persistent credential footprint in the database
    \item Eliminates long-term credential theft risks
    \item Perfect for compliance-sensitive environments requiring credential rotation
    \item Automatically scales to unlimited concurrent users without pool exhaustion
\end{itemize}

\textbf{Three-Tier Strategy Rationale:}

This tiered approach provides operational flexibility while maintaining security:
\begin{itemize}[leftmargin=*]
    \item \textbf{Performance:} Personal accounts eliminate runtime provisioning latency
    \item \textbf{Scalability:} Shared pools handle moderate concurrency efficiently
    \item \textbf{Security:} Ephemeral accounts provide maximum protection when needed
    \item \textbf{Cost Efficiency:} Reduces database account sprawl in large deployments
    \item \textbf{Compliance:} Ephemeral accounts satisfy strict credential rotation policies
\end{itemize}

\subsection{Query Policy Engine}
\label{subsec:query-policy-engine}

The query policy engine provides administrators with fine-grained, declarative control over which SQL operations are permitted, warned, or blocked. Policies are defined as named templates and assigned to roles, allowing different users to operate under different restrictions against the same database.

\subsubsection{Safety Templates}

Safety templates (\texttt{internal/api/safety\_templates.go}) are named rule sets applied per role. Each template has an \textbf{enforcement mode}:

\begin{itemize}[leftmargin=*]
    \item \textbf{Permissive:} Rules produce warnings and audit logs without blocking execution
    \item \textbf{Strict (default):} Rules block execution and return an error to the client
\end{itemize}

Each rule within a template specifies:
\begin{itemize}[leftmargin=*]
    \item \textbf{Action:} \texttt{block}, \texttt{warn}, \texttt{require\_where}, or \texttt{allow}
    \item \textbf{Condition Logic:} AND / OR combining multiple condition clauses
    \item \textbf{Conditions:} Evaluated against query type, target table, target column, query text pattern
    \item \textbf{Exceptions:} Whitelist clauses that override the rule for specific users or query patterns
    \item \textbf{Custom Error Message:} Surfaced to the client when the rule fires
\end{itemize}

Rules are evaluated using an AST-aware SQL parser, enabling table- and column-level targeting without fragile regex matching.

\subsubsection{Warned Query Review Workflow}

When a safety rule fires with the \texttt{warn} action, execution is suspended and the query enters an asynchronous admin-review workflow:

\begin{enumerate}[leftmargin=*]
    \item Query text, normalized form, rule name, session metadata, and expiry timestamp are written to the \texttt{warned\_queries} table with status \texttt{pending}
    \item User receives an immediate response indicating the query is awaiting review
    \item Admin sees a notification in the WebUI (\texttt{/admin/pending-reviews})
    \item Admin may \textbf{approve} (\texttt{POST /api/admin/warned-queries/\{id\}/approve}): query is executed against the backend and results are stored; the user is notified via \texttt{GET /api/review-notifications}
    \item Admin may \textbf{deny} (\texttt{POST /api/admin/warned-queries/\{id\}/deny}): query is discarded and user receives a rejection notice
    \item If the query returns data, results are available for download as CSV (\texttt{GET /api/review-notifications/\{id\}/download})
    \item Expired, unreviewed queries are automatically cleaned up by a background task
\end{enumerate}

Per-role query rate limits constrain how many queries a user in a given role may execute per unit time:

\begin{itemize}[leftmargin=*]
    \item \textbf{Queries per second (QPS):} Sustained request rate ceiling
    \item \textbf{Burst size:} Maximum instantaneous burst above the QPS limit
    \item \textbf{Time window (ms):} Rolling window for burst calculation
\end{itemize}

Rate limits are fully administrator-managed via \texttt{/api/admin/rate-limits/\{role-name\}}. Real-time utilisation is visible via \texttt{GET /api/admin/rate-limits/\{role-name\}/stats}. Requests exceeding the limit are rejected at the interceptor layer before reaching the backend.

\subsection{Data Masking Architecture}
\label{subsec:masking-architecture}

zGate provides three complementary, independently configurable masking strategies that operate in sequence on every result row. Together they ensure that sensitive data is never returned to clients who do not require it, regardless of the underlying database's own access controls.

\subsubsection{Column-Level Masking Policies}

Column masking policies (\texttt{internal/api/masking.go}) allow administrators to define explicit masking rules targeting a specific \textit{(role, database, table, column)} combination. Each rule specifies a \textbf{strategy}:

\begin{itemize}[leftmargin=*]
    \item \textbf{replace:} Substitute the value with a fixed string
    \item \textbf{redact:} Replace entirely with \texttt{*****}
    \item \textbf{partial:} Show only a prefix/suffix of the value (configurable length)
    \item \textbf{hash:} Return a deterministic SHA-256 hash of the value
    \item \textbf{mask:} Apply a format-preserving pattern (e.g., preserve email domain)
\end{itemize}

Policies may be defined directly (\texttt{masking\_policies}) or grouped into reusable \textbf{masking templates} (\texttt{masking\_templates}) that are then assigned to roles via \texttt{role\_masking\_templates}.

\subsubsection{AI Semantic Column Masking}

AI masking (\texttt{internal/proxy/interceptor/ai\_masking.go}) leverages the configured LLM to classify columns by semantic data type and apply masking based on the classification, rather than column name patterns.

\textbf{Classification Pipeline:}
\begin{enumerate}[leftmargin=*]
    \item The schema cache worker periodically queries all registered backend databases and submits column names/types in batches to the LLM classifier
    \item The LLM returns a semantic type for each column: \texttt{SSN}, \texttt{Email}, \texttt{Phone}, \texttt{CreditCard}, \texttt{Address}, \texttt{Name}, \texttt{DateOfBirth}, etc.
    \item Classifications are stored in \texttt{ai\_column\_classifications} with a confidence score
    \item Admins configure \textbf{AI masking templates} specifying which semantic types a role is allowed to see in plaintext; all other classified columns are masked
    \item At query time, the interceptor resolves the column's classification from cache and applies the appropriate masking function
\end{enumerate}

\begin{figure}[H]
    \centering
    % [PLACEHOLDER: AI column classification pipeline – schema cache → LLM → classification store → interceptor → masked result]
    \fbox{\parbox{0.75\textwidth}{\centering\vspace{1.5cm}\textit{[PLACEHOLDER: AI Semantic Column Classification and Masking Pipeline]}\vspace{1.5cm}}}
    \caption{AI-Powered Semantic Column Masking}

This approach masks sensitive columns even if they have non-obvious names (e.g., a column named \texttt{val1} containing Social Security Numbers), which rule-based column masking alone cannot detect.

\subsubsection{Row-Level Masking (Data Filtering)}

Row masking (\texttt{internal/proxy/interceptor/row\_masking\_interceptor.go}) silently drops rows from a result set that match configurable filter conditions, implementing row-level security without any changes to the backend database.

\textbf{Filter Conditions:}

Rules specify a \textit{(table, column, operator, value)} predicate. Supported operators:

\begin{center}
\begin{tabular}{ll}
\texttt{eq} / \texttt{neq} & Exact equality / inequality \\
\texttt{contains} / \texttt{starts\_with} / \texttt{ends\_with} & String matching \\
\texttt{in} & Membership in a value list \\
\texttt{gt} / \texttt{lt} / \texttt{gte} / \texttt{lte} & Numeric comparison \\
\texttt{between} & Inclusive range (\texttt{value\_from} -- \texttt{value\_to}) \\
\end{tabular}
\end{center}

Row masking templates are assigned to roles via \texttt{role\_row\_masking\_templates}. A role may have multiple templates, each targeting different tables, enabling fine-grained data-partition access without database-level row policies.

\subsection{Anomaly Detection}
\label{subsec:anomaly-detection}

The anomaly detection subsystem continuously monitors query behaviour per session and raises alerts when patterns deviate from the user's or role's established baseline.

\subsubsection{Detection Signals}

The anomaly interceptor (\texttt{internal/proxy/interceptor/anomaly.go}) evaluates each query against multiple behavioural signals:

\begin{itemize}[leftmargin=*]
    \item \textbf{Rate anomaly:} Sudden spike in queries per minute beyond the rolling average
    \item \textbf{Table scope anomaly:} Access to tables not queried by this user historically
    \item \textbf{Result size anomaly:} Rows returned significantly exceeding the user's historical average
    \item \textbf{Time anomaly:} Queries executed outside the user's normal working hours
    \item \textbf{Sequential scan pattern:} Systematic table enumeration indicative of data exfiltration
\end{itemize}

\subsubsection{Alert Structure}

Each alert is written to \texttt{anomaly\_notifications} with:

\begin{itemize}[leftmargin=*]
    \item \textbf{severity:} Low / medium / high / critical
    \item \textbf{score:} Numeric risk score (0–100)
    \item \textbf{reasons:} JSON array of human-readable explanation strings
    \item \textbf{correlation\_id:} Groups related alerts from the same attack sequence
    \item \textbf{session / connection / user references:} For drill-down investigation
\end{itemize}

Administrators review alerts via \texttt{GET /api/admin/anomaly-notifications} with filtering by severity and status. Aggregated statistics are available at \texttt{GET /api/admin/anomaly-stats}. Alerts can be dismissed individually, by correlation group, or all at once.

\begin{itemize}[leftmargin=*]

\begin{enumerate}[leftmargin=*]

    \item CLI creates listener on localhost:0 (random port allocation)
    \item CLI returns localhost:port to user
    \item User's database client connects to localhost
    \item CLI accepts connection and dials zGate server
    \item Bidirectional \texttt{io.Copy} between local and remote connections
\end{enumerate}

\subsubsection{Headless Tunnel Command}

The \texttt{zgate tunnel} command provides a headless, scriptable loopback tunnel designed for service accounts and CI/CD automation:

\begin{itemize}[leftmargin=*]
    \item \textbf{Authentication:} mTLS certificate (\texttt{--cert} / \texttt{--key} / \texttt{--ca} flags) — no password prompt
    \item \textbf{Local binding:} \texttt{--local-port} (0 = OS-assigned random port)
    \item \textbf{Remote target:} \texttt{--remote-host} / \texttt{--remote-port} / \texttt{--sni}
    \item Writes the local port to stdout on startup so calling scripts can pick it up
    \item Exits cleanly when the connection terminates or on SIGTERM
\end{itemize}

\subsubsection{Certificate Management Commands}

\texttt{zgate cert} provides self-service mTLS certificate lifecycle management:

\begin{itemize}[leftmargin=*]
    \item \textbf{cert status:} Display local certificate fingerprint, validity period, and expiration
    \item \textbf{cert rotate:} Request a fresh certificate from the server (\texttt{POST /api/auth/me/issue-certificate}); the CLI automatically trusts the server CA reported by \texttt{GET /api/config}
    \item \textbf{cert clear:} Delete local certificate artefacts without revoking on the server (for cleanup)
\end{itemize}

\subsection{Data Storage Architecture}

The system utilises MySQL as the database for configuration, credentials, and audit data. MySQL was chosen for its ACID compliance, row-level locking support (required for the shared account concurrency model), and proven performance for the access patterns.

\subsubsection{Database Schema}

The store has grown to cover all platform subsystems. Key table groups:

\textbf{Core Identity and Access:}
\begin{itemize}[leftmargin=*]
    \item \textbf{accounts:} Users and admins with bcrypt passwords, roles, tier, TOTP secret, and certificate fields
    \item \textbf{user\_roles:} Many-to-many user-to-role assignments
    \item \textbf{roles:} Role definitions
    \item \textbf{role\_permissions:} Role-to-database permission levels
    \item \textbf{user\_custom\_permissions:} User-level permission overrides
    \item \textbf{refresh\_tokens:} Token rotation tracking with family IDs and revocation support
    \item \textbf{revoked\_access\_tokens:} JWT revocation list (JTI + expiry for cleanup)
\end{itemize}

\textbf{Database Configuration:}
\begin{itemize}[leftmargin=*]
    \item \textbf{db\_configs:} Database connections with encrypted admin credentials
    \item \textbf{database\_frameworks:} Regulatory framework assignments per database
\end{itemize}

\textbf{Account Types:}
\begin{itemize}[leftmargin=*]
    \item \textbf{user\_db\_accounts:} Personal credential assignments (user + database unique)
    \item \textbf{shared\_db\_accounts:} Shared credential pools with concurrency counters
    \item \textbf{service\_accounts:} Programmatic accounts with token, IP allowlist, certificate fields
    \item \textbf{service\_account\_certificates:} Certificate fingerprint and revocation tracking
\end{itemize}

\textbf{PKI:}
\begin{itemize}[leftmargin=*]
    \item \textbf{pki\_ca:} Singleton internal CA (cert PEM + encrypted private key)
    \item \textbf{account\_certificates:} Human user certificate fingerprints, serials, validity, revocation
\end{itemize}

\textbf{Query Policy Engine:}
\begin{itemize}[leftmargin=*]
    \item \textbf{safety\_templates:} Named rule sets with enforcement mode and optional framework ownership
    \item \textbf{safety\_template\_rules:} Individual rules (action, condition logic, custom error message)
    \item \textbf{rule\_conditions:} Condition clauses (type, operator, value, negation, grouping)
    \item \textbf{rule\_exceptions:} Whitelist exception clauses
    \item \textbf{role\_safety\_templates:} Template-to-role assignments
    \item \textbf{warned\_queries:} Warned query review workflow (status, execution tracking, results, expiry)
    \item \textbf{role\_rate\_limits:} Per-role rate limit configuration (QPS, burst, window)
\end{itemize}

\textbf{Data Masking:}
\begin{itemize}[leftmargin=*]
    \item \textbf{masking\_policies:} Direct column masking assignments (role, database, table, column, strategy)
    \item \textbf{masking\_templates / masking\_template\_rules / role\_masking\_templates:} Reusable column masking sets
    \item \textbf{ai\_column\_classifications:} LLM-generated semantic type per (database, table, column) with confidence score
    \item \textbf{ai\_masking\_templates / role\_ai\_masking\_templates:} AI masking policy sets assigned to roles
    \item \textbf{row\_masking\_templates / row\_masking\_template\_rules / role\_row\_masking\_templates:} Row filter conditions and role assignments
\end{itemize}

\textbf{Anomaly Detection and Compliance:}
\begin{itemize}[leftmargin=*]
    \item \textbf{anomaly\_notifications:} Alerts with severity, score, reasons JSON, correlation ID, and status
    \item \textbf{framework\_exceptions:} Custom exception overrides for framework-owned rules
\end{itemize}

\textbf{AI and Chat:}
\begin{itemize}[leftmargin=*]
    \item \textbf{llm\_config:} Singleton LLM provider configuration with encrypted API key
    \item \textbf{chat\_conversations:} Conversation thread metadata
    \item \textbf{chat\_messages:} Individual messages with role, content type, and optional \texttt{proposal\_data} JSON
\end{itemize}

\subsubsection{Migration System}

The store implements an automatic schema migration system that:
\begin{itemize}[leftmargin=*]
    \item Applies incremental schema changes on startup
    \item Tracks applied migrations to prevent duplicate application
    \item Ensures backward compatibility during upgrades
    \item Supports data migrations for schema transformations
\end{itemize}

\subsection{Security Architecture}

The system implements defence-in-depth security with multiple layers of protection spanning authentication, transport, query analysis, data handling, and administrative operations.

\subsubsection{Credential Protection}

\begin{itemize}[leftmargin=*]
    \item \textbf{User Passwords:} bcrypt hashing with salt (cost factor 10)
    \item \textbf{Database Credentials:} Stored encrypted in MySQL (AES-256-GCM), decrypted only in memory during connection
    \item \textbf{JWT Tokens:} HS256 signing with secret key, 15-minute access token expiration
    \item \textbf{Refresh Tokens:} Cryptographically random, stored hashed, single-use (rotation on every refresh)
    \item \textbf{LLM API Keys:} AES-256-GCM encrypted at rest in \texttt{llm\_config}
    \item \textbf{Service Account Secrets:} One-token-at-a-time model; rotation invalidates the previous token immediately
\end{itemize}

\subsubsection{Network Security}

\begin{itemize}[leftmargin=*]
    \item \textbf{TLS Support:} Optional end-to-end TLS from client to database; standard server TLS available for JDBC clients
    \item \textbf{Mutual TLS (mTLS):} Internal CA issues client certificates; strict mode (\texttt{ENFORCE\_MTLS}) disables all legacy credential exchange
    \item \textbf{Certificate Revocation:} In-memory revocation cache; revocation terminates active sessions immediately without restart
    \item \textbf{Certificate Pinning:} Strict certificate verification for backend databases
    \item \textbf{Proxy Authentication:} Users present fake credentials to the proxy; real credentials are injected at the wire-protocol layer
    \item \textbf{Port Isolation:} Each session on a dedicated dynamically allocated port prevents cross-session attacks
    \item \textbf{IP Allowlist:} Service accounts may be restricted to specific source IP ranges
    \item \textbf{Slowloris Defence:} Protocol-level read timeouts (5-second default) prevent connection exhaustion from slow clients
\end{itemize}

\subsubsection{Anti-Bot and Rate-Limiting Protection}

\begin{itemize}[leftmargin=*]
    \item \textbf{ALTCHA Proof-of-Work:} Client must spend CPU time before login attempts; replay detection via HMAC
    \item \textbf{Arithmetic Puzzle:} Alternative lightweight challenge for environments where PoW is impractical
    \item \textbf{Per-Role Query Rate Limits:} Configurable QPS and burst limits enforced at the interceptor layer
    \item \textbf{Challenge Rate Limiting:} Challenge generation endpoints are rate-limited independently to prevent DDoS amplification
\end{itemize}

\subsubsection{Audit and Compliance}

\begin{itemize}[leftmargin=*]
    \item \textbf{Immutable Query Logs:} All queries logged with user attribution and execution metadata
    \item \textbf{Session Tracking:} Complete session lifecycle recorded (connect, queries, disconnect)
    \item \textbf{Warned Query Trail:} Admin review decisions and execution results permanently recorded
    \item \textbf{Anomaly Alerts:} Behavioural anomalies scored and logged with correlation tracking
    \item \textbf{Data Masking:} Sensitive data redacted via three complementary masking strategies before reaching the client
    \item \textbf{Regulatory Frameworks:} Automated compliance policy configuration for HIPAA, PCI-DSS, SOC2, GDPR, CCPA, and NIST
    \item \textbf{Admin Tier Enforcement:} Least-privilege admin model ensures auditors cannot modify data and policy admins cannot access credentials
\end{itemize}

\subsection{Architecture Quality Attributes}

The zGate platform is engineered with six foundational quality attributes that define its operational characteristics and production readiness. These attributes guide architectural decisions and validate the system's suitability for enterprise environments.

\subsubsection{Security: Zero Trust by Design}

\textbf{Architectural Guarantees:}
\begin{itemize}[leftmargin=*]
    \item \textbf{Credential Elimination:} End users never access or store production database credentials
    \item \textbf{Wire-Protocol Interception:} All database traffic passes through the security enforcement layer
    \item \textbf{Comprehensive Audit Trail:} Every query, connection, and authentication event logged immutably
    \item \textbf{Defence in Depth:} Multiple security layers: authentication (local/OIDC/mTLS), anti-bot challenges, RBAC, query safety rules, column masking, row filtering, AI semantic masking, anomaly detection
    \item \textbf{Ephemeral Credentials:} Temporary accounts self-destruct on disconnect; zero persistent footprint
    \item \textbf{Mutual TLS:} Internal CA enforces client identity at the transport layer
    \item \textbf{Regulatory Automation:} Built-in compliance frameworks eliminate manual policy configuration errors
\end{itemize}

\textit{Security Posture:} The architecture assumes breach and enforces Zero Trust at every layer, eliminating single points of credential compromise.

\subsubsection{Scalability: Horizontal and Vertical Growth}

\textbf{Scaling Characteristics:}
\begin{itemize}[leftmargin=*]
    \item \textbf{Stateless API:} JWT-based authentication enables load balancer distribution without session affinity
    \item \textbf{Shared Session State:} Centralized MySQL store allows multiple gateway instances
    \item \textbf{Efficient Protocol Handling:} Go goroutines provide lightweight concurrency (10,000+ simultaneous connections)
    \item \textbf{Minimal Per-Connection Overhead:} $<$5 MB memory per active session
    \item \textbf{Dynamic Port Allocation:} Operating system manages ephemeral port pool
    \item \textbf{Connection Pooling:} Shared and ephemeral accounts reduce backend database load
\end{itemize}

\textit{Scaling Strategy:} Horizontal scaling through multiple gateway instances, vertical scaling through connection pooling and efficient Go runtime.

\subsubsection{Maintainability: Clean Architecture Principles}

\textbf{Design Characteristics:}
\begin{itemize}[leftmargin=*]
    \item \textbf{Component Separation:} Clear boundaries between Gateway, API, Store, Policy, Masking, Compliance, AI, and Protocol layers
    \item \textbf{Interface-Based Design:} Protocol handlers implement a common interface for database abstraction
    \item \textbf{Dependency Injection:} Components receive dependencies explicitly, not via globals
    \item \textbf{Comprehensive Logging:} Structured logs with correlation IDs for distributed tracing
    \item \textbf{Error Propagation:} Explicit error handling with context preservation
\end{itemize}

\textit{Maintenance Philosophy:} Code organization prioritizes clarity over cleverness, with explicit dependencies and minimal coupling.

\subsubsection{Extensibility: Modular and Composable}

\textbf{Extension Points:}
\begin{itemize}[leftmargin=*]
    \item \textbf{Interceptor Pipeline:} Pluggable query processing stages; new interceptors implement a single interface and are inserted into the composite chain
    \item \textbf{Protocol Handler Interface:} Add new database protocols by implementing the Handler interface
    \item \textbf{LLM Provider:} New AI providers added by implementing the LLM client interface (currently: Ollama, OpenAI, Anthropic, Gemini, Azure)
    \item \textbf{Compliance Frameworks:} New regulatory frameworks registered by implementing the framework interface with predefined templates
    \item \textbf{Authentication Providers:} Extensible to LDAP, SAML via AuthService interface (OIDC already implemented)
    \item \textbf{Storage Backends:} MySQL is the active storage backend; the unified Store interface is designed to support additional backends
    \item \textbf{Middleware Stack:} HTTP middleware chain for cross-cutting concerns
\end{itemize}

\textit{Extension Philosophy:} Open/Closed principle — open for extension via interfaces, closed for modification of core logic.

\subsubsection{Performance: Low-Latency Proxying}

\textbf{Performance Characteristics:}
\begin{itemize}[leftmargin=*]
    \item \textbf{Proxy Overhead:} Typically $<$1 ms latency added by zGate layer
    \item \textbf{Wire Protocol Efficiency:} Zero serialization — packets forwarded directly
    \item \textbf{Connection Pooling:} Shared accounts reduce backend connection establishment overhead
    \item \textbf{Go Runtime Performance:} Compiled binary, no garbage collection pauses during I/O
    \item \textbf{Efficient Goroutines:} Lightweight threads with $<$2 KB stack overhead
    \item \textbf{Memory Efficiency:} Streaming query results without buffering entire result sets
    \item \textbf{Schema Cache:} Pre-fetched column metadata eliminates per-query schema lookups for masking
\end{itemize}

\textit{Performance Target:} Sub-millisecond overhead for query proxying, supporting thousands of concurrent connections per instance.

\subsubsection{Reliability: Fault Tolerance and Recovery}

\textbf{Reliability Mechanisms:}
\begin{itemize}[leftmargin=*]
    \item \textbf{Graceful Degradation:} Shared pool exhaustion falls back to ephemeral accounts; AI masking cache miss falls back to rule-based masking
    \item \textbf{Automatic Cleanup:} Session goroutines clean up resources on disconnect or panic
    \item \textbf{Error Recovery:} Panic handlers prevent single-connection failures from crashing the gateway
    \item \textbf{Health Checks:} \texttt{/healthz} and \texttt{/readyz} endpoints for orchestration platforms
    \item \textbf{Connection Timeout:} Configurable timeouts prevent resource leaks from slow or abandoned clients
    \item \textbf{Audit Continuity:} Failed queries logged before rejection; anomaly detection fires on errors via OnError hook
    \item \textbf{Background Workers:} Schema cache and Keycloak sync workers run independently with their own error recovery
\end{itemize}

\textit{Reliability Goal:} 99.9\% uptime for the gateway layer, with automatic recovery from transient failures and comprehensive logging for post-mortem analysis.
