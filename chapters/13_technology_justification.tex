\begin{sectionintro}{13}{Technology Justification}{
  \begin{itemize}[leftmargin=1.5em]
    \item Go for high-performance, memory-safe gateway proxy
    \item MySQL with AES-256-GCM for encrypted control-plane storage
    \item HashiCorp Vault for secrets lifecycle management
    \item Keycloak and OpenID Connect for federated identity
    \item OpenTelemetry for standards-based observability
    \item Next.js, React 19, TypeScript, and Tailwind CSS for the admin dashboard
    \item Bubble Tea TUI and Cobra for the developer CLI
    \item Internal ECDSA P-256 PKI and implemented mTLS gateway
    \item SQL parsing engines aligned with database wire protocols
    \item Docker Compose for reproducible deployment orchestration
  \end{itemize}
}
Technology selection for a Zero-Trust Database Access Gateway is not incidental---each choice directly determines the security guarantees, regulatory compliance posture, and operational reliability the system can provide. This chapter justifies every major technology decision in the zGate stack by tracing it to specific technical requirements, international standards, and architectural constraints. Choices span four components: the Go backend server and gateway proxy, the MySQL-backed encrypted control-plane store, the identity and secrets infrastructure (Keycloak, HashiCorp Vault), the observability stack (OpenTelemetry, Prometheus, Jaeger), the Next.js administration dashboard, and the Bubble Tea terminal-user-interface CLI. Each technology is evaluated against alternatives, and the rationale is grounded in concrete implementation evidence from the codebase.
\end{sectionintro}

\section{Go for the Backend Gateway and Proxy}
% ──────────────────────────────────────────────────────────────────────────────

The selection of Go (Golang) as the primary implementation language for the zGate server and gateway proxy was driven by a set of requirements that are unique to security-critical, high-throughput network infrastructure: goroutine-level concurrency, memory safety without a managed runtime, a production-grade standard library for TCP and TLS, and a single-binary deployment model that minimises the attack surface.

\subsection{Concurrency Model: Goroutines and Channels}

A database access proxy must handle thousands of simultaneous client connections, each requiring independent state (authentication context, query interceptor state, credential mapping, and an upstream TCP tunnel to the backend database). Traditional OS-thread-per-connection models impose a 1--8\,MB stack overhead per thread~\cite{go-spec}, making them impractical at scale. Go's goroutines start with a 2\,KB stack that grows on demand under the runtime's management, enabling tens of thousands of concurrent proxy sessions on modest hardware without exhausting virtual memory.

Go channels provide a first-class, deadlock-safe mechanism for coordinating goroutines. In the zGate gateway, channels are used to pass authenticated connection objects from the \texttt{Acceptor} to protocol dispatcher goroutines and to broadcast graceful-shutdown signals across the listener pool---patterns that would require explicit locking and condition variables in C++ or Java and that are common sources of race conditions in those ecosystems.

\subsection{Memory Safety and Security Posture}

Unlike C or C++, Go is a memory-safe language: bounds-checked array accesses, garbage-collected heap, and no pointer arithmetic eliminate entire classes of vulnerabilities that have historically devastated network proxies---buffer overflows, use-after-free exploits, and heap-spray attacks. The Heartbleed vulnerability (CVE-2014-0160), which exposed millions of private keys via a single-byte out-of-bounds read in OpenSSL's C implementation, is structurally impossible in a correctly written Go program. For a security gateway that sits on the boundary between untrusted clients and sensitive databases, this class-level elimination of memory-corruption vulnerabilities is a non-negotiable design criterion.

\subsection{Standard Library: \texttt{net}, \texttt{crypto/tls}, and \texttt{crypto/x509}}

Go's standard library was designed by the team that built Google's production networking infrastructure. The \texttt{net} package provides low-level TCP primitives (deadline management, \texttt{SO\_KEEPALIVE}, half-close control) that are essential for a proxy implementing three-way handshake teardown correctly across MySQL, PostgreSQL, and MSSQL wire protocols. The \texttt{crypto/tls} package implements TLS 1.3 by default, enforces secure cipher suites, and supports mutual authentication through a single \texttt{tls.Config} field---the same configuration used in zGate's \texttt{mtlsListener} (\path{internal/gateway/mtls\_listener.go}):

\begin{verbatim}
tlsCfg := &tls.Config{
    ClientAuth:           tls.RequireAndVerifyClientCert,
    ClientCAs:            deps.CAManager.ClientCAs(),
    MinVersion:           tls.VersionTLS13,
    SessionTicketsDisabled: true,
}
\end{verbatim}

Session ticket resumption is explicitly disabled so that a revoked client certificate cannot bypass the real-time revocation cache through a cached session. This decision maps directly to NIST SP 800-52 Rev.\ 2 guidance on TLS session management~\cite{nist-tls}.

\subsection{Static Binary Deployment}

Go compiles to a single, statically linked binary with all dependencies included. The zGate server image is built in a two-stage Docker build: a Go builder stage compiles the binary, and a \texttt{gcr.io/distroless/base} final stage contains only the binary and its minimal OS dependencies---no shell, no package manager, no interpreter. The resulting image surface is orders of magnitude smaller than a Node.js or JVM-based equivalent, directly reducing the number of CVE-relevant components that must be patched.

\subsection{Ecosystem Fit: SQL Parsing and Protocol Libraries}

Go's ecosystem provides production-grade libraries for the exact domain zGate occupies. The \texttt{vitess.io/vitess} library (developed and maintained by PlanetScale, originally for YouTube's MySQL sharding infrastructure) exposes a full MySQL SQL AST parser used by zGate's query interceptor to classify statements, extract table and column references, and apply safety-rule conditions without executing the query. Similarly, \texttt{github.com/pganalyze/pg\_query\_go/v5} provides a Go binding to the official PostgreSQL parser---the same parser used inside the PostgreSQL server---guaranteeing that no syntactically valid PostgreSQL query can evade interception due to parser divergence. These library choices are discussed further in Section~\ref{sec:sql-parsing}.

\section{MySQL for the Encrypted Control-Plane Store}
\label{sec:mysql-store}
% ──────────────────────────────────────────────────────────────────────────────

The zGate control-plane---user accounts, roles, permissions, database registrations, session state, safety templates, compliance frameworks, and revocation records---is persisted in a MySQL database accessed via \texttt{github.com/go-sql-driver/mysql}. This choice is distinct from the backend target databases (which may be MySQL, PostgreSQL, or MSSQL); the control-plane store is a dedicated MySQL instance managed entirely by zGate and not accessible by end users.

\subsection{Why a Relational Store Over Flat Files}

An earlier design considered YAML flat files for configuration storage. This approach was rejected because:

\begin{itemize}
    \item \textbf{No atomic multi-record updates:} Policy changes that affect multiple tables (e.g., revoking a role and simultaneously invalidating its session tickets) cannot be made atomically in flat files, risking a partially applied state on crash.
    \item \textbf{No live queries:} YAML requires full load into memory at startup; any change requires an application restart, introducing downtime.
    \item \textbf{No referential integrity:} Foreign-key relationships between users, roles, permissions, and databases must be enforced manually in application code, creating a class of consistency bugs.
    \item \textbf{Poor scaling:} A compliance catalog seeded at startup contains hundreds of safety-rule records; querying or filtering them in memory requires custom indexing logic that a SQL engine provides natively.
\end{itemize}

MySQL's ACID transaction model (\texttt{BEGIN} / \texttt{COMMIT} / \texttt{ROLLBACK}) eliminates the first and third concerns; its query engine eliminates the fourth. Live configuration updates---adding a database, revoking a role, enabling a compliance template---are committed instantly and reflected in the next request without restarting the gateway.

\subsection{AES-256-GCM Encryption of Sensitive Columns}

A relational store alone does not satisfy Zero Trust principles if the data it contains is readable to any process that can read the database files. zGate addresses this through a field-level encryption layer implemented in \path{internal/store/crypto.go}: all sensitive columns (database passwords, service-account secrets, CA private keys, TOTP seeds, refresh-token hashes) are encrypted with AES-256 in Galois/Counter Mode (GCM) before being written to MySQL and decrypted on read:

\begin{verbatim}
gcm, _ := cipher.NewGCM(aes.NewCipher(s.encryptionKey))
nonce := make([]byte, gcm.NonceSize())
io.ReadFull(rand.Reader, nonce)
ciphertext := gcm.Seal(nonce, nonce, plaintext, nil)
\end{verbatim}

A 128-bit (12-byte) nonce is generated via \texttt{crypto/rand} for each encryption operation, making ciphertext non-deterministic. GCM's built-in authentication tag detects any tampering with the ciphertext before decryption proceeds. The encryption key is a 32-byte (256-bit) secret loaded from the \texttt{ZGATE\_STORE\_KEY} environment variable, which is injected at container start via HashiCorp Vault (Section~\ref{sec:vault})---it is never written to disk or committed to source control. This design satisfies FIPS 197~\cite{fips-197} (AES), NIST SP 800-38D (GCM mode), and NIST SP 800-53 Rev.\ 5 control SC-28 (protection of information at rest)~\cite{nist-controls}.

\subsection{Row-Level Locking and the Shared-Account Pool}

zGate's shared database account model requires that exactly one active session holds a shared credential at a time. This mutual exclusion is implemented using \texttt{SELECT \ldots FOR UPDATE} on the shared-accounts table within a transaction, which MySQL's InnoDB engine enforces at the row level. This is a capability that file-based or embedded stores without row-level locking (e.g., plain SQLite in WAL mode) cannot provide safely under concurrent gateway connections.

\section{HashiCorp Vault for Secrets Lifecycle Management}
\label{sec:vault}
% ──────────────────────────────────────────────────────────────────────────────

Sensitive values---database master passwords, the \texttt{ZGATE\_STORE\_KEY} encryption key, SMTP credentials, and Keycloak client secrets---must never appear in source control, container images, or deployment scripts. The \texttt{docker-compose.yml} orchestration uses HashiCorp Vault as the secrets backend for all zGate services.

\subsection{AppRole Authentication}

The zGate server authenticates to Vault using the AppRole auth method: a \texttt{role\_id} (non-secret) identifies the application, and a \texttt{secret\_id} (short-lived, single-use) proves possession at startup. The \texttt{secret\_id} is delivered to the container via a Vault init container and expires after first use, so it cannot be replayed from a captured environment. This satisfies NIST SP 800-53 IA-5 (Authenticator Management) and SC-12 (Cryptographic Key Management)~\cite{nist-controls}.

\subsection{Dynamic Secrets and Lease Renewal}

Vault's dynamic secrets engine can generate database credentials with a bounded lease (e.g., 1 hour). When a lease expires, Vault automatically revokes the credentials at the database level. This model means that even if a credential is intercepted, it self-expires without administrator intervention---a concrete implementation of the ``assume breach'' tenet of Zero Trust Architecture (NIST SP 800-207~\cite{nist-zt}). The Go integration uses the official \texttt{github.com/hashicorp/vault/api} client with AppRole-specific helpers from \texttt{github.com/hashicorp/vault/api/auth/approle}.

\subsection{Why Vault Over Alternatives}

Environment variables provide no rotation, expiry, or access auditing. Cloud-provider secret stores (AWS Secrets Manager, Azure Key Vault) introduce a vendor dependency and require cloud-specific IAM configuration incompatible with on-premises deployments. Vault provides a vendor-neutral, self-hosted solution with open-source licensing, a well-defined audit log, and a Go SDK maintained by the same organisation that produces the server---reducing the risk of API incompatibility across versions.

\section{Keycloak and OpenID Connect for Federated Identity}
\label{sec:keycloak}
% ──────────────────────────────────────────────────────────────────────────────

zGate supports two authentication paths: a native JWT path for lightweight deployments and an OIDC path for enterprise environments that already operate an identity provider. The OIDC integration is built on Keycloak, an open-source identity and access management server developed by Red Hat, using the standard \texttt{github.com/coreos/go-oidc/v3} library for token verification.

\subsection{OpenID Connect Core 1.0}

OpenID Connect (OIDC) is a standards-track identity layer built on OAuth 2.0, published by the OpenID Foundation~\cite{oidc-core}. OIDC provides cryptographically verifiable identity tokens (ID tokens) signed with the provider's private key, with a JWKS (JSON Web Key Set) endpoint for public-key distribution. The \texttt{OIDCVerifier} in \path{internal/auth/oidc.go} performs provider discovery, fetches the JWKS, and verifies the token signature, audience (\texttt{aud}), issuer (\texttt{iss}), and expiry on every protected API request---no shared secret is required between the server and the identity provider.

\subsection{Realm-Level Role Mapping}

Keycloak assigns realm roles (e.g., \texttt{super}, \texttt{db\_admin}, \texttt{policy\_admin}, \texttt{auditor}) to user accounts, and these roles are embedded in the JWT \texttt{realm\_access.roles} claim. The \texttt{OIDCClaims.IsAdmin()} method checks for the presence of any of the four admin-tier roles, enabling seamless onboarding of enterprise users without a separate zGate account-provisioning step. This architecture supports NIST SP 800-53 IA-8 (Identification and Authentication of Non-Organisational Users) and SC-12 (Cryptographic Key Management)~\cite{nist-controls}.

\subsection{Google Social Login and Multi-Factor Authentication}

The Keycloak realm is configured with a Google Identity Provider (IdP) for social login and with TOTP (RFC 6238~\cite{rfc-6238}) for CLI device-flow MFA. The TOTP implementation uses the \texttt{github.com/pquerna/otp} library, which generates RFC 6238-compliant time-based one-time passwords with a 30-second window and SHA-1 HMAC, compatible with Google Authenticator and every major TOTP client. Keycloak's per-flow authentication policies allow MFA to be selectively enforced for the CLI device flow while permitting SSO sessions for browser-based admin logins---a separation that prevents forced re-enrolment for administrators who authenticate via an enterprise SSO provider that itself enforces MFA.

\subsection{ALTCHA Proof-of-Work Anti-Bot Protection}

Both the Keycloak login form and the native zGate login endpoint are protected by ALTCHA~\cite{altcha-spec}, an open-source proof-of-work challenge system. The server issues a challenge signed with HMAC-SHA256 (\texttt{ZGATE\_ALTCHA\_HMAC\_KEY}); the client must find a nonce $n$ such that $\text{SHA-256}(\text{challenge} \,\|\, n) < \text{threshold}$, requiring approximately 500\,000 hash evaluations on average before a solution is valid. This makes automated credential-stuffing attacks computationally expensive without adding friction for human users. The implementation uses \texttt{altcha-lib} on the backend and the \texttt{altcha} web component on the frontend. ALTCHA satisfies NIST SP 800-53 AC-7 (Unsuccessful Logon Attempts)~\cite{nist-controls}.

\section{OpenTelemetry for Standards-Based Observability}
\label{sec:otel}
% ──────────────────────────────────────────────────────────────────────────────

Production-grade security infrastructure requires comprehensive, vendor-neutral observability: distributed traces to diagnose latency across service boundaries, metrics to detect anomalies and capacity exhaustion, and structured logs to satisfy audit requirements. zGate implements the OpenTelemetry (OTel) specification~\cite{otel-spec} for all three signal types.

\subsection{Why OpenTelemetry Over Proprietary SDKs}

OpenTelemetry is a Cloud Native Computing Foundation (CNCF) incubating project that provides a vendor-neutral API, SDK, and wire protocol (OTLP) for telemetry data. Adopting OTel means that zGate's traces, metrics, and logs can be routed to any OTel-compatible backend---Jaeger for tracing, Prometheus for metrics scraping, Loki or Elasticsearch for log ingestion---by changing the OTel Collector configuration rather than modifying application code. This vendor neutrality is critical for on-premises enterprise deployments where the observability backend is mandated by policy, not chosen by the application team.

\subsection{Three-Signal Implementation}

The \path{internal/telemetry/telemetry.go} package initialises all three OTel signals at server startup:

\begin{itemize}
    \item \textbf{Traces:} A \texttt{BatchSpanProcessor} exports trace spans over OTLP/gRPC to the OTel Collector, which forwards them to a Jaeger all-in-one container. The Gorilla Mux HTTP server is instrumented via \texttt{otelmux}, automatically creating a span for every REST API request with the HTTP method, route, and status code as span attributes.
    \item \textbf{Metrics:} A \texttt{PeriodicReader} exports metrics every 15 seconds over OTLP/gRPC to the Collector, which exposes a Prometheus scrape endpoint. Go runtime metrics (goroutine count, GC pause duration, heap allocation rate, CPU utilisation) are collected automatically via \texttt{go.opentelemetry.io/contrib/instrumentation/runtime}.
    \item \textbf{Logs:} Structured log records are exported via \texttt{otlploggrpc} alongside application logs, enabling correlation of log events with trace spans using the \texttt{trace\_id} and \texttt{span\_id} fields.
\end{itemize}

Every audit log record includes an OTel trace ID, enabling an administrator investigating a policy violation to navigate directly from the zGate audit table to the distributed trace that spans the REST API call, the gateway tunnel establishment, and the database connection---a capability directly supporting NIST SP 800-53 AU-3 (Content of Audit Records)~\cite{nist-controls}.

\subsection{Prometheus and Jaeger in the Deployment Stack}

The Docker Compose deployment includes \texttt{prom/prometheus:v2.48.0} and \texttt{jaegertracing/all-in-one:1.52}. Prometheus scrapes the OTel Collector's metrics endpoint on a 15-second interval. Jaeger provides a web UI for trace search, waterfall view, and comparison. This stack is a reference implementation of the CNCF Observability Landscape best practices~\cite{cncf-landscape} and aligns with the ISO/IEC 27001:2022 Annex A control A.8.16 (Monitoring Activities)~\cite{iso27001-2022}.

\section{SQL Parsing Engines: Vitess and \texttt{pg\_query\_go}}
\label{sec:sql-parsing}
% ──────────────────────────────────────────────────────────────────────────────

The query-interception layer must parse every SQL statement before it reaches the backend database in order to classify it (SELECT, INSERT, DELETE, DDL, etc.), extract structural features (presence of WHERE clause, column list breadth, use of aggregates), and evaluate safety-rule conditions. Parser correctness is not optional---a divergence between the interceptor's parser and the database's parser could allow a carefully crafted statement to bypass a blocking rule while being accepted by the backend.

\subsection{Vitess for MySQL}

\texttt{vitess.io/vitess} is the MySQL query routing and sharding engine originally developed by YouTube~\cite{vitess-docs} and now maintained under the CNCF. Its SQL parser is a full implementation of the MySQL grammar, including extensions like \texttt{WITH} (CTEs), \texttt{WINDOW} functions, \texttt{JSON\_*} operators, and MySQL-dialect type casts. Using Vitess ensures that zGate's interceptor parses MySQL queries with the same grammar the MySQL server would accept---no syntactic edge case can produce a false negative in the safety rule engine.

\subsection{\texttt{pg\_query\_go} for PostgreSQL}

\texttt{github.com/pganalyze/pg\_query\_go/v5} provides Go bindings to \texttt{libpg\_query}, a C library that extracts the actual PostgreSQL server parser into a standalone library. Because it is the \emph{same parser} used inside PostgreSQL itself, it is provably impossible for a syntactically valid PostgreSQL statement to parse differently in the interceptor versus the backend database. This guarantee is the primary reason for choosing \texttt{pg\_query\_go} over hand-written or third-party PostgreSQL parsers~\cite{pganalyze-parser}.

\subsection{MSSQL: T-SQL Microservice}

T-SQL has no open-source Go parser with full coverage. zGate delegates T-SQL statement parsing to a dedicated \texttt{zgate-tsql-parser} microservice (containerised in the Docker Compose stack), keeping the parsing logic isolated from the main server binary and allowing independent updates to the parser without recompiling the gateway.

\section{Internal ECDSA P-256 PKI and the Implemented mTLS Gateway}
\label{sec:pki-mtls}
% ──────────────────────────────────────────────────────────────────────────────

A Zero Trust gateway cannot rely on application-layer authentication alone: the transport layer must provide cryptographic proof of identity for every connection, independent of the credential presented at the application layer. zGate implements mutual TLS (mTLS) with a fully self-managed ECDSA P-256 Certificate Authority.

\subsection{Why ECDSA P-256 Over RSA}

RSA keys at equivalent security levels (RSA-2048 $\approx$ 112-bit security; RSA-3072 $\approx$ 128-bit security) are significantly larger than ECDSA keys on the NIST P-256 curve, which provides 128-bit security with a 256-bit key. For a proxy that establishes a new TLS handshake on each incoming connection, the computational cost of ECDSA signature verification is substantially lower than RSA, directly reducing connection-establishment latency. ECDSA P-256 is specified in FIPS 186-4~\cite{fips-186-4} and is one of the two cipher suites mandated by NIST SP 800-52 Rev.\ 2 for TLS 1.3~\cite{nist-tls}.

\subsection{The \texttt{CAManager}: Key Generation and Storage}

The \path{internal/pki/ca.go} \texttt{CAManager} generates a self-signed ECDSA P-256 CA certificate at first startup (\texttt{LoadOrInit}). The CA private key is immediately encrypted with the store master key (\texttt{EncryptPublic}) and written to the \texttt{ca\_certificates} table---it is never persisted in plain text. Subsequent startups load the encrypted key, decrypt it into memory, and use it to sign client certificates for service accounts. Certificate serial numbers are 128-bit cryptographically random integers generated by \texttt{crypto/rand}, satisfying the CA/Browser Forum baseline requirements for certificate serial entropy and NIST SP 800-57 randomness guidance~\cite{nist-key}.

\subsection{Revocation Without OCSP}

Real-time revocation is implemented as an in-process cache (\path{internal/pki/revocation\_cache.go}) keyed by the leaf certificate's SHA-256 fingerprint. The \texttt{mtlsListener} consults this cache in the \texttt{VerifyConnection} callback, which runs \emph{after} the TLS handshake has verified the certificate chain but \emph{before} the connection is handed to the protocol dispatcher. This design avoids the latency and availability concerns of OCSP responders while providing the same real-time revocation semantics---a compromised service account certificate is blocked within one cache-refresh interval (configurable, default 30 seconds) of an administrator marking it revoked in the admin panel.

\section{Next.js, React 19, TypeScript, and Tailwind CSS for the Admin Dashboard}
\label{sec:webui}
% ──────────────────────────────────────────────────────────────────────────────

The zGate Web Administration Dashboard is the primary control surface for configuring the gateway, managing users and roles, monitoring active sessions, and reviewing audit logs. The technology stack---Next.js 15 (App Router), React 19, TypeScript 5, Tailwind CSS 4, Radix UI, React Hook Form, and Zod---was selected for consistent type safety across the frontend, rapid iteration on the UI without redeploying the Go backend, and accessibility compliance.

\subsection{Next.js 15 with the App Router}

Next.js 15 provides server-side rendering (SSR) and React Server Components (RSC) through the App Router, enabling the dashboard's authentication-gated pages to render their initial HTML on the server with verified session state---reducing the attack surface of client-side token handling~\cite{nextjs-docs}. The App Router's file-system-based routing maps directly to the zGate admin page hierarchy: \path{app/admin/databases/}, \path{app/admin/users/}, \path{app/admin/audit-logs/}, etc. The \texttt{iron-session} package provides encrypted, tamper-proof server-side session cookies, replacing the need for a client-accessible JWT in the browser---a significant improvement over traditional SPA authentication patterns from a Cross-Site Scripting (XSS) attack surface perspective.

\subsection{React 19 and Server Components}

React 19's Server Components allow data-fetching components to run exclusively on the server, keeping API keys and internal service URLs out of the browser bundle entirely. Client Components, annotated with \texttt{"use client"}, are used only for interactive elements (form inputs, toggle switches, real-time connection counters) where browser event handling is required. This hybrid rendering model reduces the client-side JavaScript bundle size, improving Time to Interactive (TTI) for administrators working on low-bandwidth connections in enterprise environments.

\subsection{TypeScript 5 for End-to-End Type Safety}

The Go backend defines strongly typed API response structures. TypeScript interfaces mirror these structures in the frontend, ensuring that any breaking change to a backend API response---adding a required field, changing a type from string to number---produces a TypeScript compilation error in the affected frontend components before the change reaches production. This compile-time contract enforcement is equivalent in principle to the type safety that Go's static type system provides on the backend, extending that guarantee across the API boundary~\cite{typescript-docs}.

Form validation uses Zod (version 3.25), a TypeScript-first schema library that generates both runtime validators and TypeScript types from a single schema definition. A Zod schema for a database registration form, for example, simultaneously validates user input at runtime and types the form's submitted data---eliminating the dual-maintenance burden of separate runtime validators and TypeScript interfaces. React Hook Form integrates with Zod via \texttt{@hookform/resolvers}, providing field-level error messages derived directly from the schema without manual error-state management.

\subsection{Tailwind CSS 4 and Radix UI}

Tailwind CSS 4 provides a utility-first styling system that eliminates the specificity conflicts endemic to global CSS in large single-page applications~\cite{tailwind-docs}. All styling is colocated with the component that consumes it, making visual regression audits straightforward: changing a component's styles cannot affect unrelated components.

Radix UI provides unstyled, accessibility-compliant primitive components (Dialogs, Dropdowns, Tooltips, Select menus, Toggle Groups) that implement the WAI-ARIA 1.2 design patterns~\cite{wai-aria}. Using Radix primitives ensures that the dashboard is navigable by keyboard and by screen readers out of the box, satisfying Web Content Accessibility Guidelines (WCAG) 2.1 Level AA. The Radix primitives are wrapped with Tailwind utility classes to match the zGate design system.

\subsection{FingerprintJS for Device Binding}

The dashboard uses \texttt{@fingerprintjs/fingerprintjs} to generate a stable, privacy-preserving browser fingerprint. This fingerprint is embedded in the login request and bound to the issued session token, so that a stolen session cookie cannot be replayed from a different browser without triggering a fingerprint mismatch. This mechanism supplements the server-side \texttt{iron-session} cookie encryption with a second factor that cannot be forged by an attacker who only has access to the cookie value.

\section{Bubble Tea TUI and Cobra for the Developer CLI}
\label{sec:cli}
% ──────────────────────────────────────────────────────────────────────────────

The zGate CLI (\texttt{zGate-CLI/}) is the primary interface for database developers and data engineers who need to request database connections, list accessible databases, and monitor active sessions from the terminal. The CLI is built on Cobra for command-line argument parsing and Bubble Tea for the interactive terminal user interface (TUI).

\subsection{Cobra: Standard-Library-Quality CLI Infrastructure}

Cobra is the de facto standard for Go CLI applications, used by Kubernetes (\texttt{kubectl}), Helm, GitHub CLI (\texttt{gh}), and Hugo, among others~\cite{cobra-docs}. It provides POSIX-compliant flag parsing, automatic usage generation, shell autocompletion scripts (Bash, Zsh, Fish), and a composable command hierarchy. zGate's CLI commands---\texttt{login}, \texttt{connect}, \texttt{list}, \texttt{logout}, \texttt{status}, and \texttt{active-logins}---are each implemented as Cobra \texttt{Command} objects with strongly typed flag definitions, enabling consistent behaviour across operating systems without platform-specific parsing code.

\subsection{Bubble Tea: The Elm Architecture for Terminal UIs}

Bubble Tea implements the Elm Architecture (Model-Update-View) for terminal applications~\cite{bubbletea-docs}. The Model holds immutable application state; the Update function applies messages (key presses, API responses, timer ticks) to produce a new Model; the View function renders the Model to a string that replaces the terminal output. This unidirectional data flow makes the TUI's behaviour deterministic and straightforward to test---the test suite simulates key events and API responses as messages and asserts on the resulting Model state without requiring a real terminal.

The interactive \texttt{connect} command, for example, presents a searchable list of databases the user is permitted to access, a dropdown for connection parameters, a real-time status indicator showing handshake progress, and a live SQL prompt with command history---all implemented as Bubble Tea components. The Bubble Tea and Lipgloss libraries are maintained by Charm~\cite{bubbletea-docs}, a company with a track record of long-term maintenance and semantic-versioned releases.

\subsection{OS Keyring for Credential Storage}

JWT access and refresh tokens are stored in the operating system's native credential store via \texttt{github.com/zalando/go-keyring}: Keychain on macOS, Secret Service (GNOME Keyring or KWallet) on Linux, and Windows Credential Manager on Windows. This approach keeps tokens out of plain-text files on disk (preventing credentials from appearing in accidental \texttt{cat} output, shell history, or backup snapshots) while supporting single-sign-on across terminal sessions. The go-keyring library provides a unified API across all three platforms, eliminating platform-specific credential management code in the CLI.

\section{Docker Compose for Reproducible Deployment}
\label{sec:docker}
% ──────────────────────────────────────────────────────────────────────────────

The full zGate stack comprises nine services: Vault, Keycloak, MySQL, the zGate server, the TSQL parser microservice, the WebUI, the OTel Collector, Jaeger, and Prometheus. Coordinating these services manually would require operator-specific startup scripts and introduce environment drift between development, staging, and production. Docker Compose addresses this through a declarative \texttt{docker-compose.yml} that specifies image versions, environment variable injection, health check conditions, inter-service dependency ordering, and network isolation in a single file committed to source control.

\subsection{Service Dependency and Health Check Orchestration}

Docker Compose's \texttt{depends\_on.condition: service\_healthy} ensures that Keycloak does not start until Vault and MySQL pass their health checks, and that the zGate server does not start until Keycloak has completed its realm import. This ordering prevents race conditions where a service starts before its dependencies are ready to accept connections---a common source of startup failures in multi-container deployments.

\subsection{OCI Container Standard}

All container images are built to the Open Container Initiative (OCI) Image Specification~\cite{oci-spec}, ensuring that images built for Docker Compose can be deployed on any OCI-compliant runtime (containerd, CRI-O, Podman) without modification. The Go server and WebUI images use multi-stage builds to produce minimal production images. The distroless base image for the Go server contains no shell, no package manager, and no C library beyond what Go's \texttt{net} package requires, reducing the number of CVE-relevant packages to near zero.
