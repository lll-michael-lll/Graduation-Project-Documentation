\section{Introduction and Methodology}

The zGate Database Proxy operates as an intercepting gateway within a Zero Trust architecture, serving as the single point of enforcement for access control, query safety, and data masking between client applications and backend database servers. Because the gateway handles raw database credentials, decrypts transport layer security (TLS) connections, and makes real-time access-control decisions, it is a high-value target for adversaries. 

To systematically analyze the security posture of the platform, this chapter conducts a formal threat modeling exercise. The methodology integrates multiple security review frameworks:
\begin{itemize}[leftmargin=*]
    \item \textbf{Asset-Based Risk Analysis:} Identifying the system's sensitive data, credentials, and cryptographic material, and mapping their security classification and impact.
    \item \textbf{Trust Boundary Analysis:} Defining the interfaces where data transitions between different levels of administrative control and trust.
    \item \textbf{STRIDE Threat Categorization:} Evaluating the system against Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, and Elevation of Privilege threats.
    \item \textbf{Abuse Case Scenarios:} Constructing concrete adversary paths based on realistic system configurations and potential logic flaws.
\end{itemize}

The scope of this threat model covers the three primary architectural layers of the platform: the Go-based API and Gateway Server (\texttt{zGate-Server}), the React/Next.js Web UI dashboard (\texttt{zGate-WebUI}), and the Bubble Tea-based Command Line Interface (\texttt{zgate-cli}).

\subsection{Asset Details and Security Requirements}

\subsubsection{AST-01: Vault AppRole SecretID}
The AppRole credentials (\texttt{VAULT\_ROLE\_ID} and \texttt{VAULT\_SECRET\_ID}) allow the API server to authenticate against HashiCorp Vault. This asset requires the highest level of protection since Vault stores the client private keys (\texttt{client\_key} field in KV-v2 path \texttt{secret/data/zgate/connections}) used by the proxy to dial backend databases in mutual TLS (mTLS) mode.

\subsubsection{AST-02: Target Database Credentials}
These are the usernames and passwords used to log in to target database servers (MySQL, PostgreSQL, MSSQL). They are stored either in HashiCorp Vault or encrypted within the local database store. If leaked, an attacker can bypass zGate entirely and connect directly to the database backends.

\subsubsection{AST-03: JWT Signing Secret}
The key (\texttt{ZGATE\_JWT\_SECRET}) is used by the Go authentication server to sign access tokens (valid for 5 minutes) and refresh tokens (valid for 1 hour). If compromised, an attacker can forge administratively privileged JWTs, bypassing both Web UI and CLI authentication checks.

\subsubsection{AST-04: Internal CA Private Key}
The private key of the internal Certificate Authority (CA) is generated at first boot (or loaded from the \texttt{pki\_ca} table). It is stored in the database encrypted with AES-256-GCM. A compromise of this key allows an attacker to generate valid client certificates, rendering mTLS authentication on proxy listeners ineffective.

\subsubsection{AST-05: Active Session Tickets}
During user login or CLI connect, the API generates a cryptographically random, base64url-encoded 32-byte single-use ticket stored in the \texttt{TicketStore} with a 60-second TTL. This ticket is used as the proxy password during the wire-protocol handshake.

\subsubsection{AST-06: Audit Logs and Alert Data}
Audit logs (stored in \texttt{./logs} and the database) record all queries executed through the proxy, including masked values, execution times, and target schemas. These must be tamper-resistant to prevent malicious operators from erasing their trails.

\subsection{Defined Trust Boundaries}

\subsubsection{TB-01: Client-to-API Port Boundary}
This boundary separates untrusted client agents (browsers running Next.js dashboards, headless CLI requests) from the API/HTTPS server on port 8080. Data passing through this boundary must go through rate limiting, anti-bot puzzle challenges, and JWT authentication middleware.

\subsubsection{TB-02: Client-to-Proxy Port Boundary}
This boundary separates database client applications (such as DBeaver, JDBC drivers, or command-line clients) from the protocol-aware proxy listeners. The client must present a valid 32-byte single-use ticket or complete an mTLS handshake.

\subsubsection{TB-03: Server-to-Vault Boundary}
This boundary separates the zGate API server process from HashiCorp Vault. The server authenticates using AppRole. This boundary is critical because it controls access to client private keys used for target database connection routing.

\subsubsection{TB-04: Server-to-Target Database Boundary}
This boundary handles communication from the zGate proxy dispatcher to target databases. If target databases do not enforce mTLS or certificate verification, credentials may be exposed on the wire inside the internal network.

\subsection{Data Flow Security Classifications}

The primary security-critical data flows are defined and classified below:

\subsubsection{DF-01: User Authentication Flow}
\begin{itemize}[leftmargin=*]
    \item \textbf{Path:} Client $\rightarrow$ API Server (\texttt{POST /api/login} or \texttt{/api/auth/oidc/exchange}).
    \item \textbf{Data Transmitted:} Username, password, TOTP code, or Keycloak identity token.
    \item \textbf{Classification:} \textbf{Restricted}.
    \item \textbf{Security Control:} Enforced TLS (HTTPS), rate limits per IP, and anti-bot validation (ALTCHA proof-of-work or arithmetic puzzle challenge).
\end{itemize}

\subsubsection{DF-02: Session Connection and Ticket Minting Flow}
\begin{itemize}[leftmargin=*]
    \item \textbf{Path:} CLI $\rightarrow$ API Server (\texttt{POST /api/sessions}).
    \item \textbf{Data Transmitted:} Database target ID, request parameters. Returns a minted 32-byte session ticket and dynamic TCP port.
    \item \textbf{Classification:} \textbf{Confidential}.
    \item \textbf{Security Control:} JWT bearer token verification, role-based access control (RBAC) permission resolution, and database status check.
\end{itemize}

\subsubsection{DF-03: Proxy Connection and Query Dispatch Flow}
\begin{itemize}[leftmargin=*]
    \item \textbf{Path:} Database Client $\rightarrow$ Proxy Port $\rightarrow$ Target Database.
    \item \textbf{Data Transmitted:} Raw database protocol handshake, database queries, and row-structured results.
    \item \textbf{Classification:} \textbf{Confidential}.
    \item \textbf{Security Control:} Ticket validation or mTLS certificate check, before-query safety rules (safety templates), column masking, and after-query anomaly scoring.
\end{itemize}

\section{Attack Surface Analysis}

The system exposes multiple entry points across its network listeners and deployment configurations, which can be grouped into distinct attack surfaces:

\subsection{External Network Attack Surface}
\begin{itemize}[leftmargin=*]
    \item \textbf{HTTPS REST API (Port 8080):} Hosts login and administration endpoints. Vulnerabilities like session hijacking, CSRF, and broken object-level authorization (BOLA) must be controlled here.
    \item \textbf{Database Proxy Listeners (Ports 3306, 5432, 1433):} Binds public TCP ports to accept MySQL, PostgreSQL, and MSSQL connections. Exposed to protocol fuzzing and denial-of-service (Slowloris) attacks during the initial connection handshake.
\end{itemize}

\subsection{Administrative Attack Surface}
\begin{itemize}[leftmargin=*]
    \item \textbf{Admin Tier Control Endpoints:} Bounded by administrative role tiers (\texttt{db\_admin}, \texttt{policy\_admin}, \texttt{auditor}, and \texttt{super}). Enforced via \texttt{tierMiddleware} in the server. A failure in this middleware would expose administrative functions, such as user modification or safety template disabling, to regular users.
    \item \textbf{MFA/TOTP Reset Endpoint:} The internal TOTP reset path (\texttt{/api/internal/totp/reset}) uses a shared secret for authentication. If this secret is exposed, an attacker can disable MFA for any administrative account.
\end{itemize}

\subsection{Infrastructure and Supply Chain Surface}
\begin{itemize}[leftmargin=*]
    \item \textbf{Go Dependency Graph:} The server uses third-party libraries for JWT handling (\texttt{golang-jwt/jwt/v5}), OIDC validation (\texttt{go-oidc/v3}), and MySQL protocol parsing (\texttt{go-mysql}). Security flaws in these packages could lead to remote code execution (RCE) or denial of service.
    \item \textbf{Docker Deployment Environment:} The deployment relies on environment files (\texttt{.env}) to pass sensitive parameters like database root passwords, JWT secrets, and Vault role secrets. Insecure permissions on these files could expose credentials to other users on the host system.
\end{itemize}

\section{STRIDE Analysis of Core Components}

This section evaluates the primary functional components of the zGate system against the STRIDE threat model categories.

\subsection{API Server and Authentication Engine}

The API server manages user credentials, OAuth/OIDC validation, and TOTP checks.

\subsubsection{S --- Spoofing: JWT Signature Forgery}
\begin{itemize}[leftmargin=*]
    \item \textbf{Threat Description:} An attacker creates a signed JWT with administrative claims by exploiting a weak or default \texttt{ZGATE\_JWT\_SECRET}.
    \item \textbf{Attack Scenario:} If the system is deployed using a default development secret (e.g., \texttt{"secret"}), the attacker can sign a token with \texttt{"is\_admin": true} and \texttt{"tier": "super"} and send it to administrative API routes.
    \item \textbf{Mitigation:} The system must require a strong secret key at startup, enforcing a minimum entropy check during initialization in \texttt{auth.Init()}.
\end{itemize}

\subsubsection{T --- Tampering: TOTP Code Replay}
\begin{itemize}[leftmargin=*]
    \item \textbf{Threat Description:} An attacker intercepts a valid TOTP token and replays it within the 30-second validity window.
    \item \textbf{Attack Scenario:} The attacker captures the user's password and a active TOTP code via a proxy or network tap, then quickly submits a duplicate login request.
    \item \textbf{Mitigation:} Implement a short-lived cache in the auth server to track used TOTP codes, rejecting duplicate submissions within the current time step.
\end{itemize}

\subsubsection{R --- Repudiation: Administrative Activity Deletion}
\begin{itemize}[leftmargin=*]
    \item \textbf{Threat Description:} A compromised database administrator deletes system events or audit log rows to cover their tracks.
    \item \textbf{Attack Scenario:} A compromised account with the \texttt{db\_admin} tier runs direct delete queries against the \texttt{system\_events} table.
    \item \textbf{Mitigation:} Write system logs to a local append-only file system (\texttt{./logs}) and configure forwarding to an external, read-only log management system.
\end{itemize}

\subsubsection{I --- Information Disclosure: Cleartext Password Exposure}
\begin{itemize}[leftmargin=*]
    \item \textbf{Threat Description:} User or administrator passwords are exposed in cleartext within application logs.
    \item \textbf{Attack Scenario:} The login handler encounters an error and prints the incoming request structure (including the password field) to the logger.
    \item \textbf{Mitigation:} Explicitly sanitize the request body before logging, and verify that fields like \texttt{Password} are never passed to log wrappers.
\end{itemize}

\subsubsection{E --- Elevation of Privilege: Administrative Tier Escalation}
\begin{itemize}[leftmargin=*]
    \item \textbf{Threat Description:} An administrator with a lower tier escalates their access to a higher tier.
    \item \textbf{Attack Scenario:} An administrator with the \texttt{db\_admin} tier submits a request to \texttt{PATCH /api/admin/admins/\{username\}/tier} to promote themselves to \texttt{super}.
    \item \textbf{Mitigation:} The \texttt{SetAdminTier} function in \texttt{AdminService} validates that only a user who already holds the \texttt{super} tier can perform tier promotions.
\end{itemize}

\subsection{Proxy Connection Manager and Dispatcher}

The proxy layer processes database protocol packets, parses SQL queries, and applies security policies.

\subsubsection{S --- Spoofing: Connection Ticket Hijacking}
\begin{itemize}[leftmargin=*]
    \item \textbf{Threat Description:} An attacker intercepts a valid connection ticket and connects to the proxy port before the legitimate user.
    \item \textbf{Attack Scenario:} The attacker steals a dynamic ticket returned by \texttt{POST /api/sessions} and uses it to connect to the allocated proxy listener.
    \item \textbf{Mitigation:} Dynamic tickets must be single-use (consumed immediately on connection) and have a short TTL (e.g., 60 seconds). Additionally, bind tickets to the source IP address that requested the session.
\end{itemize}

\subsubsection{T --- Tampering: Safety Parser Evasion}
\begin{itemize}[leftmargin=*]
    \item \textbf{Threat Description:} An attacker bypasses safety templates by using nested SQL, CTEs, or proprietary database syntax.
    \item \textbf{Attack Scenario:} An attacker bypasses a block rule on the \texttt{employees} table by writing a nested query or utilizing a database-specific feature like CTEs.
    \item \textbf{Mitigation:} Use an AST-aware SQL parser (\texttt{pingcap/tidb/parser}) to parse queries before evaluation, rather than relying on regex matchers.
\end{itemize}

\subsubsection{I --- Information Disclosure: AI Classifier Masking Failures}
\begin{itemize}[leftmargin=*]
    \item \textbf{Threat Description:} Sensitive data (like PII) is exposed in cleartext because the AI column classifier fails or times out.
    \item \textbf{Attack Scenario:} The HTTP call to the AI classification service times out, causing the proxy to default to an unmasked state for unknown columns.
    \item \textbf{Mitigation:} Enforce a fail-safe policy. If the classifier is unavailable, columns matching sensitive name patterns must default to masked.
\end{itemize}

\subsubsection{D --- Denial of Service: Handshake Connection Exhaustion (Slowloris)}
\begin{itemize}[leftmargin=*]
    \item \textbf{Threat Description:} An attacker opens many TCP connections on the proxy ports and does not send handshake data, exhausting system file descriptors.
    \item \textbf{Attack Scenario:} An attacker executes a Slowloris-style attack against the proxy listener, causing new client connections to hang.
    \item \textbf{Mitigation:} Implement a read timeout on the initial connection handshake. In \texttt{PeekRouting}, connections that fail to send database protocol data within 10 seconds must be closed.
\end{itemize}

\subsection{Internal PKI and CA Module}

The PKI engine manages client certificates used for mTLS.

\subsubsection{S --- Spoofing: CA Private Key Leakage}
\begin{itemize}[leftmargin=*]
    \item \textbf{Threat Description:} An attacker extracts the CA private key and signs rogue client certificates.
    \item \textbf{Attack Scenario:} An attacker obtains read access to the database configuration store, reads the encrypted CA row, and decrypts it by finding the master key in the environment variables.
    \item \textbf{Mitigation:} The master key used to decrypt the CA key must be stored securely (e.g., in a secret manager like Vault) rather than a plaintext environment file.
\end{itemize}

\subsubsection{T --- Tampering: Stale Revocation Cache}
\begin{itemize}[leftmargin=*]
    \item \textbf{Threat Description:} An administrator revokes a certificate, but the user continues to connect because the proxy uses a cached revocation state.
    \item \textbf{Attack Scenario:} An admin revokes a user certificate via the API, but the active proxy sessions continue because the revocation cache TTL has not expired.
    \item \textbf{Mitigation:} When a certificate is revoked, trigger a direct callback to the proxy manager to terminate all active sessions associated with that certificate's fingerprint.
\end{itemize}

\begin{itemize}[leftmargin=*]
    \item \textbf{Context:} A service account is configured to access two databases: \texttt{db\_prod\_billing} (Restricted) and \texttt{db\_dev\_sandbox} (Internal). The service account has active sessions open for both.
    \item \textbf{Attack Path:}
    \begin{enumerate}
        \item The attacker gains access to the service account client credentials on a developer machine.
        \item The attacker attempts a connection to the proxy port. Since the service account holds active sessions for both databases, a naive username-only resolution in the proxy manager might non-deterministically select either database connection.
        \item By repeatedly connecting, the attacker eventually gets routed to \texttt{db\_prod\_billing} despite only intending to access the sandbox database.
    \end{enumerate}
    \item \textbf{Remediation:} The resolution logic in \texttt{ResolveUniqueDatabaseForUser} must check the target database name during the connection handshake. If a user has multiple active sessions, connection requests without a matching database target name must be rejected.
\end{itemize}

\subsection{Abuse Case B: SQL Parser Evasion using Dialect-Specific CTE Tricks}
\begin{itemize}[leftmargin=*]
    \item \textbf{Context:} The safety templates block write access to the \texttt{salary\_history} table.
    \item \textbf{Attack Path:}
    \begin{enumerate}
        \item The attacker drafts a write statement nested inside a CTE structure:
        \begin{verbatim}
        WITH malicious_cte AS (
            UPDATE salary_history SET salary = 999999 WHERE user_id = 42
            RETURNING 1
        ) SELECT 1;
        \end{verbatim}
        \item The proxy uses a general parser that does not correctly parse database-specific CTE write actions, classifying the query as a read-only \texttt{SELECT}.
        \item The query is forwarded to the backend PostgreSQL database, which supports updates inside CTEs, executing the unauthorized change.
    \end{enumerate}
    \item \textbf{Remediation:} Configure the query analyzer to enforce strict SQL dialect validation matching the target database type. Any query containing syntax structures not recognized by the AST parser must be blocked.
\end{itemize}

\subsection{Abuse Case C: Keycloak-to-DB Out-of-Sync Administrative Lockout}
\begin{itemize}[leftmargin=*]
    \item \textbf{Context:} An administrator is suspended in Keycloak due to suspected credential compromise.
    \item \textbf{Attack Path:}
    \begin{enumerate}
        \item The administrator's account is deactivated in Keycloak.
        \item A background sync job fails (e.g., due to a temporary network issue, recorded as a \texttt{keycloakSyncFailed} system event).
        \item The administrator's session and refresh tokens remain valid on the local zGate server for their remaining lifetime.
        \item The attacker uses the compromised administrator's active session to access the admin dashboard and modify database permissions before the local session expires.
    \end{enumerate}
    \item \textbf{Remediation:} The Web UI and API server must perform real-time verification of the OIDC token state with Keycloak for high-privilege operations, rather than relying solely on local JWT lifetime checks.
\end{itemize}

\section{Strategic Security Recommendations}

To improve the security posture of the zGate Database Proxy, the following recommendations are structured by implementation timeline:

\subsection{Immediate Actions (0---30 Days)}
\begin{enumerate}[leftmargin=*]
    \item \textbf{Enforce mTLS in Production:} Set \texttt{ENFORCE\_MTLS=true} in production environments to disable the ticket-based auth fallback, removing the threat of connection ticket interception.
    \item \textbf{Add TOTP Replay Prevention:} Modify the TOTP login verification code to record the last validated time step for each user, blocking multiple login requests using the same code within a 30-second window.
    \item \textbf{Verify JWT Secret Entropy:} Enforce a check during server startup in \texttt{auth.Init()} to ensure that the configured JWT secret meets a minimum length (e.g., at least 256 bits).
\end{enumerate}

\subsection{Short-Term Actions (1---3 Months)}
\begin{enumerate}[leftmargin=*]
    \item \textbf{Implement Handshake Timeouts:} Enforce a strict 10-second timeout on initial packet reads inside the proxy listeners' \texttt{PeekRouting} phase to prevent TCP file descriptor exhaustion from Slowloris attacks.
    \item \textbf{Monitor Sync Failures:} Configure automated alerts for \texttt{keycloakSyncFailed} events in the \texttt{system\_events} store to notify security administrators if user accounts fail to sync with Keycloak.
